# Як працює авторизація MasterQuiz

Реалізація з `feature/auth` інтегрована в `develop` через PR #4. Перевірено з Java-бекендом
`2a30955` та Next.js 16.3.8. Верстка логіну й реєстрації збережена; повідомлення
валідації відображаються лише після спроби відправлення форми.

## З чого почати читання коду

1. `src/app/login/page.tsx` та `src/app/register/page.tsx` читають параметри URL
   та передають їх у серверний `components/AuthPage.tsx`. Він перевіряє сесію
   та складає спільну сторінку з Header, привітання, форми й Footer.
2. `src/features/auth/components/AuthForm.tsx` складає форму з
   `AuthFormFields`, `AuthSubmitButton` та `AuthFormFeedback`.
   Це Client Component, бо форма реагує на введення та submit.
3. `src/features/auth/hooks/useAuthForm.ts` містить клієнтську логіку форми.
   Хук отримує `mode` та адресу переходу, повертає стани й обробники.
4. `src/features/auth/services/auth.ts` виконує браузерні HTTP-запити.
   Хук відповідає за стан і переходи; service — за fetch та перевірку відповіді.
5. `src/features/auth/validators/auth.ts` перевіряє поля й типи вхідного JSON.
   Та сама валідація використовується в браузері та Route Handler; її публічні
   експорти залишені в `validation.ts`. Java також перевіряє дані.
6. `src/app/api/auth/[action]/route.ts` перевіряє HTTP-запит і передає
   валідний payload у `src/features/auth/server/auth.ts`. Там виконується
   обмін із Java через `server/backend.ts` і формується відповідь із cookie.
7. `src/features/auth/server/session.ts` читає cookie, перевіряє сесію
   через бекенд і встановлює/очищає cookie у відповідях Route Handlers.

`"use client"` у формі визначає клієнтську межу. Імпортований нею хук працює
в клієнтській частині; винесення функції в окремий файл не робить її серверною.
Початковий HTML Client Component також може бути сформований на сервері.
Модулі `server/` імпортують `server-only`, щоб їх не можна було випадково
підключити до браузерного коду.

## Чому така архітектура

Усі ці компоненти й правила наразі потрібні тільки авторизації, тому вони
залишаються в `features/auth`. Спільні Header/Footer лежать у `components/layout`.
Коли поле реально знадобиться іншій функції, можна винести його в
`components/ui` й прибрати auth-специфічні назви. Загальної системи форм зараз немає.

| Частина                       | Відповідальність                                              |
| ----------------------------- | ------------------------------------------------------------- |
| `components/AuthPage`         | Спільний серверний екран логіну й реєстрації                  |
| `components/AuthForm`         | Складання форми та підключення хука                           |
| `components/AuthFormFields`   | Які поля потрібні для login/register                          |
| `components/AuthField`        | Контрольований input, label та помилка поля                   |
| `components/AuthFieldIcon`    | Три SVG; іконка замка повторно використовується               |
| `components/AuthSubmitButton` | Submit, pending та стрілка                                    |
| `components/AuthFormFeedback` | Загальні помилки й повідомлення про реєстрацію                |
| `hooks/useAuthForm`           | State, submit, помилки та навігація                           |
| `services/auth`               | Браузерні запити login/register/logout до Next.js             |
| `validators/auth`             | Валідація полів і структури вхідного payload                  |
| `validators/responses`        | Перевірка API-об'єктів і читання повідомлень помилок          |
| `utils/form`                  | Початковий state і нормалізація payload без обрізання паролів |
| `utils/redirect`              | Безпечний next та адреса після login/register                 |
| `types.ts`                    | Спільні типи полів, payload, відповіді та сесії               |
| `server/auth`                 | Java login/register, відповідь і встановлення cookie          |
| `server/backend`              | Серверний fetch з Bearer, timeout та no-store                 |
| `server/session`              | Читання, перевірка та очищення cookie                         |

Стилі виділених компонентів знаходяться в їхніх SCSS Modules.
`LoginForm.module.scss` тепер містить тільки картку та відступи між частинами.
Папки `validators`, `utils` і `services` створені всередині feature та містять
реально використані файли. `types.ts` не дробиться на папку з окремим файлом
для кожного маленького типу.

## Логін: два запити

Користувач натискає Log in. `onSubmit` викликає `handleSubmit` із хука.

Поля контрольовані: хук зберігає `email`, `password`, `nickname` та
`repeatPassword` в об'єкті `values` через `useState`. Кожен input отримує
`value={values.email}` або відповідне інше поле. Його `onChange` викликає
`updateField("email", event.target.value)`: ця функція оновлює стан і очищає
попередню помилку поля.

Під час submit хук формує payload зі стану `values` через `createAuthPayload()`.
Email обрізається через `trim()`, пароль зберігається без змін. Після валідації
хук встановлює `pending=true` та викликає `submitAuth()`. Service виконує
браузерний запит:

```ts
fetch("/api/auth/login", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ email, password }),
});
```

Це запит до Next.js. Route Handler читає JSON, перевіряє поля та origin,
потім викликає `authenticate()`, який робить серверний запит до Java `/login`.
Адреса Java береться з серверної змінної `BACKEND_API_URL`; локально
за замовчуванням це `http://localhost:8080`.

Java повертає `{ token }`. Next.js читає строк дії JWT, встановлює cookie
`masterquiz_session` і повертає браузеру тільки:

```ts
{
  session: {
    (email, expiresAt);
  }
}
```

JWT не повертається в JSON і не записується у localStorage. Cookie має
`HttpOnly`, `SameSite=lax`, `Path=/`, а її `Expires` відповідає JWT `exp`.
У production також встановлюється `Secure`; локальний dev працює через HTTP.
Браузер надалі сам додає cookie до запитів на наш сайт.

Після успіху хук переходить на дозволений внутрішній `next` або на `/`
і викликає `router.refresh()`. Поля очищаються через `setValues(emptyAuthValues)`.
Server Components заново читають cookie:
Header показує email і Log out. Зовнішні адреси та повернення в auth-сторінки
не приймаються як `next`.

## Реєстрація

Поля UI називаються Email address, Username, Password, Repeat password.
Для Java Username передається як `nickname`.

JSON містить `email`, `nickname`, `password`, `repeatPassword`.
Перевіряються заповненість полів, формат email, щонайменше 8 символів
пароля та збіг паролів.

Java створює користувача та повертає `201` із `id`, `email`, `nickname`.
Next.js повертає ці поля в `{ user }`, без пароля.
Бекенд не авторизує користувача під час реєстрації, тому форма переходить
на `/login?registered=1`. На логіні відображається повідомлення про створення
акаунта. Якщо був `next`, він зберігається для майбутнього входу.

## Pending та помилки

`pending` блокує fieldset і submit, а текст кнопки змінюється на Please wait….
Додатковий `useRef` не дозволяє відправити другий запит до того, як React
встигне відрендерити заблоковану кнопку. У `finally` блокування знімається.

`fetch` не кидає виняток через HTTP 400/401/409/500. Service читає JSON
і перевіряє `response.ok`. Результат має `ok: true` або `ok: false` із помилкою;
мережеві винятки обробляє catch у хуку. `validators/responses` перевіряє
отриманий JSON, а `parseAuthError()` використовується і в браузері, і на сервері.

- Клієнтські та серверні помилки полів показуються під відповідним полем.
- Неправильний пароль повертає `401` і повідомлення під формою.
- Повторний email повертає `409`.
- Backend `errors` зберігається, а не відкидається проксі.
- Недоступний Java-сервіс, timeout або некоректна успішна відповідь
  обробляються Next.js як `502`.
- Серверний timeout — 10 секунд, браузерний — 15 секунд.

Після зміни поля його попередня помилка очищається. Серверна валідація
залишається обов'язковою: браузерні перевірки можна обійти прямим HTTP-запитом.

## Відновлення та перевірка сесії

Server Components викликають `getSession()`. Для браузерного коду є
`GET /api/auth/session`, який повертає `{ session }` або `{ session: null }`.
Ці відповіді та інші auth-відповіді мають `Cache-Control: no-store`.

Бекенд поки не має `/me`. Тому перевірка сесії використовує невеликий
захищений `GET /categories?page=0&size=1`. Саме Java перевіряє підпис JWT.
Читання `sub` та `exp` з JSON усередині токена не вважається перевіркою підпису.
Підроблений токен із майбутнім `exp` не дає авторизації.

Прострочений, пошкоджений або відхилений цим запитом токен дає `session=null`.
Route Handler перевірки сесії також очищає невалідну cookie.
Якщо Java тимчасово недоступна, маршрут повертає `503` і зберігає cookie,
щоб користувач міг повторити перевірку.

Загальний `backendFetch` бере токен із cookie та додає
`Authorization: Bearer ...` до серверних запитів. Для публічних Java
`/login` і `/register` старий токен не передається, щоб пошкоджена сесія
не перешкоджала новому входу.

Не кожен `403` означає прострочення сесії. У поточному бекенді окремі
question/category маршрути повертають `403` через свої помилки. Загальний
помічник передає їхній статус без автоматичного logout.

## Вихід та захист запитів

AuthControls викликає `logout()` із service, який виконує
`POST /api/auth/logout` із JSON `{}`. Next.js очищає
cookie, після чого клієнт переходить на `/` і оновлює Server Components.
Після перезавантаження користувач залишається неавторизованим.

Бекенд не має endpoint відкликання JWT. Logout видаляє сесію в цьому браузері;
раніше виданий bearer-токен залишається дійсним у Java до свого `exp`.

Login, register і logout перевіряють Origin та браузерний Sec-Fetch-Site,
а також вимагають JSON. Запит із чужого origin відхиляється з `403`, без
створення чи видалення сесії. Це потрібно, бо браузер автоматично надсилає cookie.

## Чого ще немає в backend-контракті

Немає refresh token, відновлення пароля, профілю `/me`, створення анонімної
сесії або її зв'язування з акаунтом. Forgot password? поки не виконує дії.
Guest access і збереження гостьового прогресу з MAS-185 потребують контракту
бекенду; ми не генеруємо вигаданий anonymous ID.

## Що перевірено

Після рефакторингу 12.10.2026 повторно пройшли typecheck, lint, build і
форматування в обох worktrees. 13 запитів до реального Java перевірили
JSON/типи полів, валідацію, Origin, реєстрацію, duplicate email, неправильний
пароль, login cookie, відновлення сесії та logout.

Браузерні перевірки підтвердили контрольовані поля, pending, збереження даних
після помилок і переходи після успіху. Координати й обчислені стилі логіну
та реєстрації на 1440, 390 і 320 px збіглися з версією до рефакторингу.
Для перевірки успішних/помилкових клієнтських відповідей використовувалися
перехоплені тестові HTTP-відповіді; серверна інтеграція перевірялася окремо
через реальний Java API.

Перевірено реальними HTTP-запитами: реєстрацію, повторний email,
неправильний пароль, login cookie, session restoration, logout, сторонній
origin, невалідні поля, пошкоджену/прострочену/підроблену cookie,
повторний вхід зі старою невалідною cookie.

У браузері перевірено порожню форму, незбіг паролів, успішну реєстрацію
з переходом на логін, неправильний та правильний пароль, Header після входу,
повне перезавантаження, перенаправлення вже авторизованого користувача,
logout і недоступність cookie для `document.cookie`.

На окремому production-сервері з контрольованим тестовим upstream перевірено
недоступність/timeout Java, некоректний JSON, відсутній token, некоректну
відповідь реєстрації, backend 500, збереження `errors`, атрибут Secure та
збереження cookie при тимчасовій помилці перевірки сесії.

`pnpm typecheck`, `pnpm lint`, форматування змінених файлів і `pnpm build`
пройшли. Для перевірок створено окремі синтетичні акаунти; наявні записи
не видалялися.
